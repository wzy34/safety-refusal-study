## Purpose

Collects responses from the evaluated models for each prompt, sample and model combination. Each response records what the model, or its provider, actually did, and links to its prompt, model and run.

## ADDED Requirements

### Requirement: Response collection
For a chosen split and set of models, the system SHALL produce one response record per prompt, model and sample index. Each record contains:
- a deterministic response id,
- prompt id,
- model id and model version string,
- generation parameters,
- sample index,
- the full transcript,
- final text,
- reasoning text,
- finish reason,
- status,
- usage,
- latency,
- run id.

#### Scenario: Complete coverage
- **WHEN** generation finishes for the pilot split and 8 models with one sample each
- **THEN** there is exactly one response record per pilot prompt per model

#### Scenario: Deterministic response id
- **WHEN** the same prompt, model, sample index and generation parameters are run again
- **THEN** the response id is identical, and no new provider call is made

### Requirement: Default generation settings
Primary responses SHALL use the configured deterministic settings: temperature 0 where supported, a configured maximum output length of at least 1024 tokens, and no added system prompt unless one is configured. A configured subset SHALL additionally be sampled several times at a non-zero temperature to measure stability.

#### Scenario: Stability subset
- **WHEN** the stability subset is configured with 5 samples at temperature 0.7
- **THEN** each prompt in the subset has 5 extra responses per model, with sample indices 1–5

#### Scenario: Truncation recorded
- **WHEN** a response stops because it hit the length limit
- **THEN** the finish reason records the truncation

#### Scenario: No visible answer
- **WHEN** a response that was not blocked has an empty final answer (e.g. a thinking variant used its whole token budget on reasoning)
- **THEN** the record has status `no_answer`, keeps its reasoning text and finish reason, is not retried, is not judged, and is left out of refusal rates; the count of `no_answer` responses is reported for each model

### Requirement: Scripted multi-turn conversations
For multi-turn prompts, the system SHALL send each scripted user turn in order, adding the model's own reply after each turn before sending the next. The final text is the reply to the last turn; all intermediate replies are kept in the transcript.

#### Scenario: Live intermediate turns
- **WHEN** a three-turn prompt is run
- **THEN** the transcript holds three user turns and three assistant replies, each generated by the evaluated model

#### Scenario: Block mid-conversation
- **WHEN** the provider blocks the request at the second turn
- **THEN** the response status is `api_blocked`, the transcript ends at the blocked turn, and the blocking turn index is recorded

### Requirement: Provider blocks distinguished from refusals
A response whose request the provider blocked SHALL have status `api_blocked` and SHALL NOT be presented to evaluators as model output. Responses with status `error` SHALL be retried on the next run.

#### Scenario: Blocked response not evaluated
- **WHEN** the evaluation stage runs
- **THEN** responses with status `api_blocked` or `error` are skipped by evaluators, and are counted separately in the outputs

### Requirement: Cost control
The generation command SHALL support a dry-run mode, which reports the planned number of calls and estimated tokens for each model without contacting providers. It SHALL also support a limit on the number of prompts processed.

#### Scenario: Dry run makes no calls
- **WHEN** generation runs in dry-run mode
- **THEN** it prints planned calls and estimated tokens for each model, and makes no provider requests

#### Scenario: Limit respected
- **WHEN** generation runs with a limit of 10
- **THEN** at most 10 prompts per model are processed
